# 아이디어 브레인스토밍

초기 아이디어: $ARGUMENTS

위 값이 비어 있으면 첫 질문으로 아이디어를 한 줄로 설명해 달라고 요청한다.

이 skill의 목표는 설계에 들어가기 전에 "이 아이디어를 만들 가치가 있는가, 만들 수 있는가"를 사용자와의 대화로 검증하고, 그 결과를 아이디어 문서 하나로 남기는 것이다. 대화가 본체이므로 모든 단계를 현재 대화 안에서 진행한다.

## 진행 규칙

- 질문은 한 번에 하나만 한다. 답을 받기 전에는 다음 질문으로 넘어가지 않는다.
- 가능하면 객관식(선택지 2~4개 + 직접 입력)으로 묻는다. 선택지를 만들 수 없을 때만 열린 질문을 쓴다.
- 성급하게 해결책을 내놓지 않는다. 설계 스펙·구현 계획·코드를 작성하지 않는다.
- 사용자의 주장을 그대로 받아들이지 않는다. 반례, 대안, 숨은 가정을 제시해 다시 검토하게 한다.
- 단계를 전환할 때는 지금까지 정리된 내용을 3~5줄로 요약하고, 사용자가 확인한 뒤에 다음 단계로 넘어간다.

## 단계

### 1. 발산

- 목표: 범위를 좁히기 전에 아이디어가 나아갈 수 있는 방향을 넓게 펼친다.
- 질문 대상: 아이디어가 나온 계기, 사용자가 떠올린 형태, 기대하는 결과. 사용자가 생각하지 못한 방향이나 변형도 2~3개 제시한다. 이는 구현 방법이 아니라 "무엇을 만들 것인가"의 방향이어야 한다.
- 산출물: 후보 방향 목록과 사용자가 이어서 다룰 방향 하나.

### 2. 명확화

- 목표: 고른 방향을 검증할 수 있을 만큼 구체화한다.
- 질문 대상 (한 번에 하나씩):
  - 해결하려는 문제
  - 대상 사용자
  - 기존 코드베이스와의 관계: 신규 프로젝트인가, 기존 코드의 확장인가
  - 제약: 기술 스택, 기한, 성능, 호환성
  - 성공 기준: 무엇이 되면 성공이라고 볼 것인가
- 산출물: 문제·대상 사용자·코드베이스 관계·제약·성공 기준 요약.

### 3. 검증

- 목표: 만들 가치가 있는지, 만들 수 있는지 판단한다.
- 할 일:
  1. 현재 저장소 조사: 저장소의 구조와 관련 코드를 읽고 기술적 실현 가능성을 판단한다. 재사용할 수 있는 부분과 충돌하는 부분을 찾는다. 신규 프로젝트이고 참고할 코드가 없으면 건너뛴다.
  2. 기존 솔루션 조사: 라이브러리·서비스·오픈소스로 이미 해결된 문제인지 확인한다. 있다면 직접 만들 이유가 남는지 사용자에게 묻는다.
  3. 리스크 식별: 기술 리스크, 범위 리스크, 유지보수 리스크를 각각 짚는다.
  4. MVP 범위 제안: 핵심 가치를 확인할 수 있는 최소 범위와 이번에 제외할 범위를 제안한다.
- 질문 대상: 조사 결과에 대한 사용자의 판단. 기존 솔루션을 쓸지, 리스크를 감수할지, 제안한 MVP 범위에 동의하는지.
- 산출물: 실현 가능성 판단, 기존 솔루션 비교, 핵심 리스크 목록, MVP 범위 초안.

### 4. 수렴

- 목표: 지금까지 검토한 내용을 하나의 제안으로 좁힌다.
- 질문 대상: 최종 방향, 기각할 대안과 그 이유, 기술 접근 개요(스택·핵심 컴포넌트 수준까지만), 남은 미해결 질문, 다음 단계.
- 산출물: 문서 필수 항목 9개에 들어갈 내용이 모두 정해진 상태.

### 5. 문서화

- 목표: 대화 결과를 아이디어 문서 하나로 남긴다.
- 질문 대상: 파일 이름으로 쓸 slug. 아이디어를 나타내는 짧은 영문 kebab-case를 제안하고 확인받는다.
- 작성 방법:
  1. 이 skill 디렉토리의 [template.md](template.md)를 읽고 헤딩 구조를 그대로 따른다. 헤딩 아래의 작성 가이드 주석은 최종 문서에서 지운다.
  2. 대화에서 확정되지 않은 내용은 추측으로 채우지 않고 "미해결 질문"에 넣는다.
  3. 아래 저장 경로에 한 번만 저장한다. 같은 경로에 파일이 이미 있으면 덮어쓰기 전에 묻는다.
- 산출물: `docs/ideas/<slug>.md`

## 완료 기준

다음 중 하나를 만족하면 문서화 단계로 들어간다. 들어가기 전에 진행 규칙대로 3~5줄 요약을 보여주고 확인받는다.

- 사용자가 "정리하자"(또는 같은 뜻의 말)라고 한다. 앞 단계가 끝나지 않았어도 문서화로 넘어가고, 채우지 못한 항목은 "미해결 질문"에 남긴다.
- 문서 필수 항목 9개가 모두 채워졌다: 문제 정의, 제안, 기술 접근 개요, MVP 범위와 제외 범위, 근거, 검토한 대안과 기각 이유, 리스크, 미해결 질문, 다음 단계.

## 저장 경로

- 최종 문서: 현재 저장소 루트 기준 `docs/ideas/<slug>.md`
- 문서화 단계에서 한 번만 저장한다. 그 전에는 어떤 파일도 만들거나 수정하지 않는다.

## subagent 위임 규칙

- 질문·요약·확인 등 사용자와의 대화는 위임하지 않고 직접 진행한다.
- 검증 단계에서 파일을 많이 읽어야 하거나 웹 조사가 필요할 때만 그 조사를 subagent에 위임한다. 파일 몇 개만 보면 되는 경우는 직접 읽는다.
  - 저장소 조사 → `Explore` agent. 명확화 단계 요약과 확인할 질문을 넘기고, 관련 파일 경로·재사용 가능한 부분·충돌 지점·실현 가능성 판단만 요약받는다.
  - 기존 솔루션 조사 → `general-purpose` agent. 아이디어 요약을 넘기고, 후보별 이름·링크·해결하는 범위·한계만 요약받는다.
- 두 조사가 서로 독립적이면 동시에 실행한다.
- subagent에는 조사만 맡긴다. 파일 수정이나 문서 작성은 맡기지 않는다.
- 결과를 그대로 옮기지 않고 핵심만 사용자에게 전달한 뒤, 그에 대한 판단을 질문 하나로 묻는다.

## 종료

문서를 저장한 뒤 아래 문구로 안내하고 skill을 끝낸다. 설계나 구현을 이어서 시작하지 않는다.

> 아이디어 문서를 `docs/ideas/<slug>.md`에 저장했습니다. 설계 단계로 넘어가려면 별도 skill이나 plan mode를 사용하세요.
